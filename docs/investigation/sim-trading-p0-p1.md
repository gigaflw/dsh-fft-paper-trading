# 模拟盘 P0/P1：选型与边界

> 决策前分析：P0/P1 要做「真实市场节奏」，哪些自己写、哪些借开源、哪些明确不做。
> 下游：[`docs/design.md`](../design.md) §19（定型设计）。
> 外部事实：[`docs/thirdparty/sim-trading-open-source.md`](../thirdparty/sim-trading-open-source.md)。

## 1 问题

v0.1 的账本、费用、T+1、复盘是可信的，但用户故事里的「按真实市场节奏」没有落地：没有交易时段、盘后能成交、收盘快照不是收盘价、没有涨跌停/部分成交/行情面。

P0 要解决「时间与成交时点」，P1 要解决「行情面、撮合真实性、复盘流水」。问题不是「功能名有没有」，而是**每条规则由谁负责、失败时怎么表现**。

## 2 运行时：是否引入现成交易引擎

| 方案 | 评价 |
| --- | --- |
| 引入 NautilusTrader 作为撮合/账户内核 | 能力最全，但 Rust/Python 运行时、LGPL-3.0、数据适配与 DSH 插件生命周期都要重接；为一个现金 A 股模拟盘过重 |
| 引入 Lean（C#） | 时段/成交模型最贴近，但 .NET 运行时与 QuantConnect 数据模型同样过重，且股票部分成交本身是 TODO |
| 复用现有 TypeScript 服务，借「模型边界」 | **选中**：`MarketClock`/`TradingCalendarPort`/`FillModel`/`AccountStore` 分层照搬思想，代码自己写；风险最小、可测试、可重放 |

**结论**：不引运行时依赖；把 Lean 的「交易所开关门 + 成交模型」、Nautilus 的「沙盒 = 实时数据 + 模拟执行 + 撮合/成交模型分层」、freqtrade 的「dry-run 行为清单」当作设计约束与验收参考。

## 3 交易日历：数据源与时段表

| 方案 | 评价 |
| --- | --- |
| `exchange_calendars`（Python） | 节假日准、有午休；但 Node 运行时引 Python 不可接受；且不建模集合竞价 |
| 自己维护节假日表 | 会随调休过期，维护成本高 |
| FTShare `ft_v1_time_trading_calendar` + 内置时段表 | **选中**：交易日来自数据，时段（含集合竞价）是交易所规则，代码里集中一处；取不到时回退工作日并标 `calendarSource` |

**结论**：日历数据 + 固定时段表分离。时段表包含 `pre_open / continuous_am / lunch / continuous_pm / auction_close / closed`；集合竞价单独建模，因为日历库都不管这一段。

## 4 行情时间：两个时间戳

v0.1 把 `quote.ts` 定义成「取数时间」，导致盘后报价永远新鲜、市价单盘后必成交（见 design §17）。

| 方案 | 评价 |
| --- | --- |
| 继续用取数时间 | 无法表达「这条报价属于哪个交易时段」 |
| `marketTs`（行情时间）+ `fetchedAt`（取数时间） | **选中**：新鲜度看 `marketTs` + 当前时段；界面可显示延迟；盘后报价明确不可成交 |

**结论**：适配器必须从 bar/成交记录取行情时间；取不到时宁可用 `marketTs = null` 标 `unknown`，也不拿当前时间冒充。

## 5 收盘/开盘与离线补算

| 方案 | 评价 |
| --- | --- |
| 宿主后台常驻任务在 15:00 写快照 | 依赖进程一直活着；DSH 退出就丢 |
| 只在用户操作时写 | 会漏日；跨多天只写一条 |
| 定时器 + 调用时幂等补算 | **选中**：`advanceTo(now)` 在每次 RPC/工具调用前跑；定时器只负责及时触发；收盘快照按交易日逐日补齐 |

**离线成交策略**：宿主不在线期间**不补成交**（freqtrade 的保守假设），只补收盘快照与 T+1；挂单保持原状态，恢复后从当前时段继续。理由：补成交会造出用户没看见的成交，破坏「等待真实时间」的语义；不补只损失真实感，不破坏账本。

## 6 撮合：在只有最新价的数据上做到什么程度

2026-10-21 实调确认：FTShare **没有买一/卖一，也没有 L2/L3 盘口**；搜索、全市场列表、实时日 K、实时分钟 K 都只有最新价/OHLC。因此：

| 能力 | 决定 |
| --- | --- |
| 市价成交 | 最新价/bar OHLC + 滑点；连续竞价才可成交；不能用 spread 定价 |
| 限价成交 | 触价/穿价才成交；用分钟 bar 的 high/low 判定；不假装逐档吃深度 |
| 部分成交 | 用分钟成交量（实测单位为股）做参与率上限（默认 10%）；没有成交量时退回全量并标记 `unlimited` |
| 涨跌停 | 由 `prevClose` + 板块比例计算；可用 `ft_v1_limit_list` 的涨跌停价/封单校准；越界拒单；涨停买/跌停卖在封死时不成交 |
| 停牌 | 优先用 `ft_v1_suspension_list`；没有列表时看 `status=Suspended`/成交量为 0；拒单 |
| 集合竞价 | 订单排队，开盘按开盘价成交；实时分钟 K 没有 09:15–09:25 bar，竞价只能靠日 K/开盘价补 |
| 止损/条件单/强平 | 不在 P1（现金账户，无杠杆） |

**结论**：明确「最新价/OHLC + 参与率上限」是模拟假设，不做假盘口；部分成交必须可重放、可解释。Lean 的股票 fill model 自己都没做 depth-limited 部分成交，说明这不是「顺手就有」的能力。

## 7 行情面：FTShare 已有什么

2026-10-21 用真实 Key 实调（探针脚本在本地 `tmp/research-p0p1/`，结果已固化进 design §19.9）：

| 能力 | 接口 | 实测结果 |
| --- | --- | --- |
| 标的搜索 | `ft_v1_search` | 返回 `symbol/name/board/close/change/change_rate`；无买卖价 |
| 全市场 A 股 | `ft_v1_daec_stocks` | 5909 只；`page_size=500` 可用；含 `st/status/prev_close/board/volume`；`ts_millis` 是快照时间 |
| 代码全集 | `ft_v1_stock_list` | 5575 条代码 + 名称 |
| 板块筛选 | `ft_v2_stock_list_filter` | `board` 枚举可用；返回 `sh/sz/sh_star/sz_chi_next/bj` |
| 停牌 | `ft_v1_suspension_list` | 当日全量停牌 + 类型/原因 |
| 涨跌停池 | `ft_v1_limit_list` | `up/down/up_break` + 涨跌停价/封单金额/开板时间 |
| 实时 1 分钟 K | `ft_v4_stock_realtime_minute_kline` | 241 根；`ts_millis` 为 bar 收盘时间；无竞价 bar；volume 为股数；收盘后返回全日 |
| 历史分钟 | `ft_v2_stock_minutes` | 区间查询可用 |
| 分时 | `ft_v4_daec_history_prices` | 241 条 `price/avg_price/volume/turnover` |
| 日/周/月 K | `ft_v1_stock_candlesticks` | 收盘后含当日 bar |
| 交易日历 | `ft_v1_time_trading_calendar` | 入参必须是 **YYYYMMDD 整数**；返回 `trade_dates` 整数数组；国庆假期正确跳过 |
| 市场快照 | `ft_v1_daec_market_snapshot` | 返回 `status=closed` 与涨跌分布 |
| 封单金额 | `ft_v2_stock_minute_seal` | 可用；非涨停股返回空 |

**结论**：搜索、列表、分时、K 线、日历都有数据源；**没有买一/卖一，更没有盘口深度**，界面只展示最新价，撮合只用最新价/OHLC。全市场 `order_by` 只验证到升序，`filter` 语法未确认，因此不做「涨幅榜」。

## 8 复盘与流水

v0.1 有成交、权益曲线、统计，但没有「资金流水」「日终」「隔夜」「回合」。

| 能力 | 做法 |
| --- | --- |
| 资金流水 | 从 `account.opened/reset` + `order.filled` 推导，不改账本；端点返回逐笔余额 |
| 日终报告 | `day.closed` 扩展收盘价/费用/持仓/T+1；新增 `day.opened` 含跳空 |
| 隔夜/跳空 | 开盘价 vs 昨收；持仓逐只计算 |
| 回合统计 | 平均成本法（与账本一致），按标的聚合；胜率/持仓时长/盈亏比 |
| 备注 | 委托可带一句 `note`，落进事件，复盘可见 |

**结论**：不新增第二套账本；所有报表从事件推导，保证与持仓/现金一致。

## 9 明确不做（本阶段）

- 保证金、卖空、强平（现金账户；要做是产品范围变更）。
- L2/L3 盘口、逐档撮合（无数据源）。
- 止损/条件单/算法单（P2）。
- 工具卡、设置写入（v0.3，与「真实节奏」无关）。
- 多账户、分红送转、通知（v0.3）。
- 时间加速/快进（永远不做，与产品前提冲突）。

## 10 待验证

**已核对（2026-10-21）**：日历返回结构与假期、搜索/列表/分钟字段、分钟成交量单位（股）、无竞价 bar、收盘后返回全日、无买一/卖一、DSH `ctx.timeout/ctx.interval` 可用。结果见 [design.md](../design.md) §19.9。

**仍未验证**：

1. 交易时段内 `ft_v4_stock_realtime_minute_kline` 的最后一根是否含当前未完成分钟（探针在收盘后）。
2. FTShare 的调用速率限制与并发行为（当前每次调用开新 MCP 会话）。
3. 涨跌停/ST 比例按交易所现行规则的文本（实现前复核；先做成配置）。
4. DSH 休眠/唤醒时 timer 的实际行为（`advanceTo` 兜底，但触发时点需实测）。

## 11 验收口径

以 design §19.9 为准；核心是五条：

1. 盘后市价单拒绝，限价单只预埋；
2. 15:00 收盘快照用收盘价，次日 09:30 才解锁 T+1；
3. 离线跨日不补成交，只补快照；
4. 部分成交可重放，剩余可撤；
5. 涨停买/跌停卖/停牌有明确拒绝码，不静默成交。
